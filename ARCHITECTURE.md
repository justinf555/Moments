# Architecture

How Moments fits together, as of October 2026. Read this before diving into the code. Rules for changing the code are in `CLAUDE.md`; build and tooling details are in `docs/dev-environment.md`; feature designs are in `docs/design-*.md`.

## Overview

Moments is a GNOME photo manager written in Rust with GTK4 and libadwaita, targeting GNOME Circle. It has two backends behind one code path:

- **Local**: photos live on disk. A library is either *managed* (originals copied into the bundle) or *referenced* (originals left where they are).
- **Immich**: an offline-first cache of an Immich server. Changes are pulled from `POST /sync/stream` and local edits are pushed back through an outbox.

Both backends share the same SQLite schema, services and UI. What differs is injected at construction: a `MutationRecorder` (does a change need pushing?) and an `OriginalResolver` (where does the original file come from?).

## Layers

```
 GTK widgets            src/ui/
     │  GObject properties, signals, gio::ListStore models
     ▼
 Clients                src/client/      MediaClientV2, AlbumClientV2, PeopleClientV2,
     │                                   ImportClient, SyncClient  (GObject singletons)
     │  async calls run on Tokio; results come back via glib::idle_add_once
     ▼
 Library services       src/library/<feature>/service/   (mod.rs core, sync.rs Immich-only)
     │  business logic; each service emits typed events
     ▼
 Repositories           src/library/<feature>/repository/   (thin sqlx wrappers)
     ▼
 Database               src/library/db/  (SqlitePool, WAL, numbered migrations)

 Beside the stack:  importer/  renderer/  sync/
```

Widgets talk only to clients. Clients own the `gio::ListStore` models the widgets bind to, and keep them current from service events. Services own business logic and events. Repositories only run SQL.

## Library

`Library` (`library/mod.rs`) is a concrete struct composing six services:

```rust
pub struct Library {
    albums: AlbumService,
    faces: FacesService,
    editing: EditingService,
    media: MediaService,
    metadata: MetadataService,
    thumbnails: ThumbnailService,
    recorder: Arc<dyn MutationRecorder>,
}
```

It is built with `Library::open(bundle, mode, db, recorder, resolver)` and accessed through `.media()`, `.albums()`, `.faces()`, `.editing()`, `.metadata()` and `.thumbnails()`. Operations that span services, such as `save_pixel_edit`, `revert_edit` and `delete_permanently`, are methods on `Library` itself.

Injected per backend:

| | Local | Immich |
|---|---|---|
| `MutationRecorder` | `NoOpRecorder`: nothing to push | `QueueWriterOutbox`: writes each change to the `sync_outbox` table |
| `OriginalResolver` | `LocalResolver`: the file is already on disk | `CachedResolver`: downloads the original into a sharded cache on first use, evicting least-recently-used, uploaded, unpinned files to stay under `originals-cache-max-mb` |

The outbox is transactional (#655): a service opens a transaction with `Database::begin()` (`BEGIN IMMEDIATE`), makes its write through the repository's `_in_tx` method, calls `recorder.record(&mut tx, …)` and commits. A recorder error propagates and rolls the write back, so a change and its outbox row land together or not at all. Events are emitted only after the commit. While a transaction is open, all reads and writes go through it, never the pool. Cross-service operations do the same with one transaction: service `_in_tx` methods return their events for the caller to emit once it commits (`MediaService::emit_committed`), and `save_pixel_edit` / `revert_edit` remove files only after the commit (#709).

### Identity and queries

- **`MediaId`** is a UUID v4 stored as 32 lowercase hex chars. It's generated locally with `MediaId::generate()`, or loaded from the DB or sync stream with `MediaId::new()`. Deduplication uses the separate `content_hash` (SHA-1, matching what Immich uses), never the ID.
- **`MediaFilter`** selects a view: `All`, `Favorites`, `Trashed`, `RecentImports { since }`, `Album { album_id }`, `Person { person_id }`. Each maps to a SQL clause in the media repository.
- **Keyset pagination**: `list_media` pages with a `MediaCursor` (sort key + id), so every page costs the same however large the library is. There are no `OFFSET` scans.

## Database

SQLite through `sqlx` with runtime-checked queries, a pool of up to 4 connections in WAL mode, and a 5 s busy timeout. The schema is built by numbered migrations in `src/library/db/migrations/`, embedded with `sqlx::migrate!`.

| Table | Holds |
|---|---|
| `media` | One row per asset: path, dates, dimensions, type, favourite/trash state, external (Immich) id, content hash |
| `media_metadata` | Full EXIF detail, loaded on demand |
| `thumbnails` | Thumbnail generation state and path |
| `albums`, `album_media` | Albums and membership |
| `people`, `asset_faces` | People and face ↔ asset links |
| `stacks` | Immich stacks (burst/bracket grouping) |
| `edits` | Non-destructive edit state per asset |
| `immich_asset_edits` | Edit state as synced to/from Immich |
| `sync_outbox` | Pending local changes to push (Immich backend) |
| `sync_checkpoints`, `sync_audit` | Pull-sync progress and audit trail |

## Events and commands

There is no central event bus. (The old `EventBus` / `CommandDispatcher` design was removed; see `docs/design-event-bus.md`.)

```
 UI action ──▶ client method ──▶ service (on Tokio) ──▶ repository
                                     │
                                     └─ emits AlbumEvent / MediaEvent / FacesEvent / ThumbnailEvent
                                              │  EventEmitter<T> fan-out (tokio mpsc)
                                              ▼
                                  client listener task (Tokio)
                                              │  glib::idle_add_once
                                              ▼
                              patch ListStore models + emit GObject signal
                                              ▼
                                  widgets (connected in realize/unrealize)
```

- **Commands** call a client method directly, e.g. `MediaClientV2::trash(ids)`. The client runs the service call on Tokio. Failures surface as toasts through `crate::client::show_error_toast`, which is safe to call from any thread.
- **Events**: each service owns a typed `EventEmitter`. Where a service emits an event, the client's listener is the one place that patches the models. Sync-initiated and user-initiated changes therefore take the same path.
- **Client signals** fan results out to widgets:
  - `MediaClientV2`: `items-trashed`, `items-restored`, `items-deleted`, `favorite-changed`.
  - `AlbumClientV2`: `album-media-changed`, `album-deleted`.

## Two executors

- **GTK main context**: the UI thread only (widgets, signal handlers, property bindings).
- **Tokio runtime**: created in `main()` and shared via `MomentsApplication::default().tokio_handle()`. It does all I/O: database, files, decoding and HTTP.

Results flow back to GTK with `glib::idle_add_once` or through client property notifications. Shared state is reached through `MomentsApplication::default()` and its typed accessors (`media_client_v2()`, `album_client_v2()`, `people_client()`, `import_client()`, `sync_client()`, `render_pipeline()`, `tokio_handle()`), never by walking the widget tree.

## UI

```
MomentsWindow (adw::ApplicationWindow)
└── main_stack
    ├── "loading"  → status page + spinner
    └── "content"  → ToastOverlay
                     └── NavigationSplitView
                         ├── sidebar: MomentsSidebar (AdwSidebar)
                         │   ├── header: activity indicator · hamburger menu (Import, Keyboard Shortcuts, About, Preferences)
                         │   ├── routes: Photos, Favorites, Recent Imports, People*, Albums, Trash
                         │   └── pinned albums section (dynamic)
                         └── content: ContentCoordinator (GtkStack)
                             ├── photos / favorites / recent / trash → photo grid (MediaFilter)
                             ├── people → people grid ─▶ photo grid (Person)
                             ├── albums → album grid  ─▶ photo grid (Album)
                             └── empty  → empty-library view
                                   photo grid ─▶ photo viewer / video viewer
```

\* People is hidden for the local backend, which has no face data.

- **Views** register with `ContentCoordinator`, eagerly or lazily (built on first navigation; see `docs/design-lazy-view-loading.md`). Each route gets its own view and model instance.
- **View actions**: each view installs its own action group as `"view"` with `insert_action_group`, and GTK resolves actions up the widget tree.
- **Activity indicator** (sidebar header): a compact spinner/icon with a detail popover, driven by `SyncClient` and `ImportClient` (`docs/design-activity-indicator.md`).
- **Photo grid**: a `GtkGridView` over a client-owned `ListStore`, with lazy `load_more()` on scroll. Its six zoom levels are saved in GSettings, and changing zoom rebuilds the cell factory. An LRU `TextureCache` plus a decode semaphore keep recycled cells cheap.
- **Viewers**: `adw::NavigationPage` subclasses pushed from the grid. The photo viewer header bar is `[★] [ℹ] [✏] [⋮]`; the video viewer's is `[★] [ℹ] [⋮]`. The overflow menu is a hand-built `gtk::Popover` with icon + label buttons, shared via `viewer/menu.rs`. Share, Export original, Set as wallpaper and Show in Files are present but hidden until implemented.
- **Edit panel**: non-destructive editing. `EditState` holds adjustments, filters and transforms; the panel renders a preview through `renderer::edits`. Saving stores the edit state; a pixel edit (`Library::save_pixel_edit`) also writes a rendered copy with the edit embedded as XMP, so it can be recovered later (#659). See `docs/design-photo-editing.md`.
- **Album picker**: an `adw::Dialog` with search, cover thumbnails, "Already added" pills and inline creation. Data is fetched first, then the dialog is built, then changes go to `AlbumClientV2` methods.
- **Templates**: almost every widget uses a Blueprint (`.blp`) template, compiled to `.ui` and bundled into GResources. See `docs/design-gobject-blueprint-refactor.md`.

## Import

`ImportPipelineBuilder` builds an `ImportPipeline`, and `ImportPipeline::run()` takes each file through six steps:

1. **discovery**: walk the sources
2. **filter**: keep supported formats
3. **hash**: SHA-1 content hash, skipping duplicates
4. **metadata**: EXIF and video metadata
5. **persistence**: copy into the bundle in managed mode, then insert the rows
6. **thumbnail**: 360 px WebP in a two-level sharded directory

The pipeline emits `ImportProgress` and returns an `ImportSummary`. `ImportClient::import_folder` first scans the chosen folder over GIO's async API on the GTK main context (the `gio::File` from the portal must be kept for Flatpak, so the walk can't move to Tokio with `std::fs`), then hands the file list to `ImportPipeline::run_files()` on Tokio. Its state runs `Idle → Scanning → Running → Complete`; `ImportClient::cancel()` stops the scan or stops the pipeline before its next file (the file in flight finishes) and the summary arrives with `cancelled` set. Progress shows in the import dialog and the activity indicator. For the Immich backend, `MediaService` records an `AssetImported` change in the outbox, and push sync uploads the file.

## Renderer

`RenderPipeline` (`renderer/pipeline.rs`) is stateless, and every consumer goes through it: thumbnail generation, full-resolution viewing and edit previews. It runs decode → orientation → resize → edits → output (RGBA or WebP).

Decoding goes through a private `FormatRegistry`, which detects the format by magic bytes and extension:

- **standard**: JPEG, PNG, WebP, TIFF, GIF, HEIC/HEIF, via `image` and `libheif-rs`
- **raw**: CR2, NEF, ARW, DNG and others, via `rawler`
- **video**: video frames via GStreamer

Moving to glycin is being evaluated in #654.

## Immich sync

`SyncHandle::start()` is called from `application/` and spawns two Tokio tasks:

- **Pull** (`pull.rs`): reads `POST /sync/stream` as NDJSON and sends each entity to a handler in `handlers/` (assets, exif, edits, albums, album membership, people, faces, stacks, lifecycle). Handlers upsert through library services, which emit events. Thumbnails download inline. Acks are flushed as it goes, so an interrupted sync resumes where it stopped. After a full cycle, a heartbeat removes local albums the server no longer has.
- **Push** (`push.rs`): drains `sync_outbox`, maps each `Mutation` to an Immich API call, and marks each entry done or failed.

The sync interval updates live: the preference value goes into a `tokio::sync::watch` channel, and the sync loop `select!`s on its sleep timer and `changed()`. The app works fully offline after the first sync. See `docs/design-immich-backend.md`, `docs/design-face-integration.md` and `docs/design-immich-edit-sync.md`.

## Settings (GSettings)

The schema is `data/io.github.justinf555.Moments.gschema.xml.in`, with the app ID as schema ID, so each channel keeps its own settings.

| Key | Purpose |
|---|---|
| `library-path` | Library bundle location (empty on first run) |
| `zoom-level` | Photo grid zoom index |
| `recent-imports-days` | Window for the Recent Imports view |
| `trash-retention-days` | Days before trash is auto-purged |
| `sync-interval-seconds` | Immich pull interval |
| `originals-cache-max-mb` | Immich originals cache limit. **Not yet enforced:** written by Preferences, read nowhere else |
| `pinned-album-ids` | Albums pinned to the sidebar |
| `album-sort-order` | Album grid sort |
| `people-unnamed-visibility`, `people-show-hidden` | People grid filters |
| `color-scheme` | Light/dark/system |
| `window-width`, `window-height`, `is-maximized` | Window state |
| `enable-adjustments`, `enable-filters` | Edit panel sections |

## Testing

- **Unit tests** sit in `#[cfg(test)]` modules beside the code, using `#[tokio::test]` for async. Run them with `make test`.
- **Integration tests** in `tests/` are headless GTK4 tests run inside a mutter Wayland session (`make test-integration`), with shared fixtures in `tests/common/`. See `docs/design-integration-testing.md`.
- **CI** runs fmt, clippy, unit tests and integration tests inside the Flatpak CI build. See `docs/dev-environment.md` for every workflow.
